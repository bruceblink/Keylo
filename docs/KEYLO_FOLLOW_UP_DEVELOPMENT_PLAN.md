# Keylo 后续开发计划

> 制定日期：2026-08-02。本文是 Keylo 当前的主线计划，替代“按 Keycloak 功能清单扩展”的推进方式。Keycloak 仍是协议和安全实践的参照，但不是待追平的产品规格。

## 1. 当前判断

Keylo 已完成轻量身份中心的可接入基线：标准 OIDC Provider、外部 OIDC 身份源、MFA、统一 Principal/RBAC、资源树、授权决策、审计、版本记录和四语言 RP 样例均已具备，并已纳入自动回归。

因此，当前最大风险不是缺少另一项协议或管理功能，而是现有能力对接入方、管理员和运维人员仍可能不够好用。继续横向实现 SAML、SCIM、Passkey、复杂多租户或 Keycloak Realm，会在没有明确收益时扩大安全面、数据迁移面和长期维护成本。

接下来按“易用性打磨 -> 可用性验证 -> 真实需求确认 -> 按触发条件扩展”推进。每个候选功能都必须同时回答：谁使用、减少了哪一步操作或哪类排障、与现有 Principal/RBAC 如何复用、如何测试和如何撤销。

## 2. 产品边界

Keylo 是轻量、可扩展的通用认证与授权中心：

- **认证**：通过 OIDC、密码、MFA 和外部身份源确认主体身份。
- **授权**：通过 Principal、角色、权限、资源树和服务端授权检查决定是否允许访问。
- **集成**：向任意标准客户端提供 OIDC/JWKS，向资源服务提供稳定授权决策接口。
- **治理**：提供密钥、会话、审计和必要的运行状态，而不复制完整企业 IAM 平台。

Keystone 是首个接入方和回归样本，不是 Keylo 的功能边界，也不应成为 Keylo 的专用依赖。

### 不纳入默认主线

- 完整 Keycloak Realm 层级、脚本策略语言和任意表达式求值。
- 仅为“协议齐全”实现的 SAML、SCIM、Device Flow、CIBA、PAR、DPoP、Token Exchange 或 Passkey。
- 未被多个实际部署验证的复杂多租户模型、事件总线和高可用拓扑。

## 3. 近期主线：2.1 易用性与可用性闭环

目标是在不增加重型平台能力的前提下，让独立团队能更少猜测、更少手工配置地部署、接入、治理和排障 Keylo。此阶段是后续功能投资的证据来源；能减少首次接入、日常授权管理或故障定位成本的改进优先于新增协议。

### 3.1 P0：自助参考接入

选择 Keystone 作为首个参考接入方，同时保持协议接口对其他系统通用。

1. 建立从部署到登录、授权检查、退出和会话撤销的可重复验收流程。
2. 固化 Keylo 与资源服务的责任边界：资源服务不得仅因 Token 可验签就放行，必须使用明确的权限或授权决策。
3. 为接入失败提供可定位的错误、审计查询路径和最小排障手册。
4. 为主流接入栈提供能直接运行的最小样例，优先减少复制配置和安全边界的理解成本。

**完成标准：** 新环境可按文档完成一次端到端接入；关键拒绝场景可从客户端响应和审计记录定位；不新增 Keystone 专用协议或数据模型。

### 3.2 P0：自助部署与运行基线

以当前支持的数据库和 Redis 依赖为范围，补齐单实例的部署、升级和恢复验证。

1. 明确配置校验、依赖就绪、密钥加载、HTTPS 默认要求和受控内网 HTTP 的边界。
2. 用可执行步骤验证数据库迁移、密钥轮换、备份恢复和失败回退。
3. 将已有健康检查、指标和审计记录组织成面向运维的最小诊断路径。
4. 优先把启动失败和不安全配置转换为可行动的提示，而不是让使用者从日志或源码猜测原因。

**完成标准：** 一套受支持环境可重复完成部署、升级、密钥轮换和恢复演练；任何未支持的 HA 或跨公网 HTTP 场景在文档和启动校验中明确拒绝或警示。

### 3.3 P1：管理与接入反馈闭环

在至少一个真实接入方完成后，记录需求而不是立即扩展实现。

每个需求记录必须包含客户端类型、主体数量、组织边界、身份来源、合规要求、威胁模型、预期协议、实际操作步骤和验收场景。优先修复重复出现的配置、授权建模或排障摩擦；只把能用小范围模型解决的需求纳入下一阶段。

**完成标准：** 形成可追溯的需求清单和一次优先级评审；没有证据的能力继续留在候选池。

## 4. 需求触发的扩展路线

下列工作没有固定日期或默认承诺，按触发条件选择其一推进；同一周期只启动一个方向。

| 触发信号 | 启动方向 | 最小范围 | 明确不做 |
| --- | --- | --- | --- |
| 两个及以上相互隔离的客户组织 | 组织边界 | `organization`、成员关系、对象归属、跨组织默认拒绝和兼容迁移 | Realm 复制、任意策略脚本 |
| 资源服务需要所有者、部门或业务上下文判断 | 受控数据范围 | 固定条件类型、服务端决策和审计原因 | 通用表达式引擎 |
| 企业目录要求自动入离职或组同步 | SCIM 2.0 | 用户/组 provisioning、禁用和会话撤销语义 | 未定义冲突语义的全量同步 |
| 已签约客户只能提供 SAML | SAML 联邦 | 单一明确的 SP 或 IdP 场景和回归样例 | 为协议数量实现的通用 SAML 平台 |
| 管理员无密码或抗钓鱼需求 | Passkey | 管理员账户的 WebAuthn 注册、登录和恢复路径 | 未经恢复流程验证的全员强制切换 |
| CLI、受限设备或受委托访问的明确场景 | 专项 OAuth 扩展 | 选择 Device Flow、DPoP 或 Token Exchange 中的一项 | 多项并行实现 |
| 多实例运行、外部审计消费已成为部署要求 | 运行治理 | 一项可验证的 Trace、Outbox/Webhook 或 HA 演练 | 未验证的分布式平台改造 |

## 5. 优先级与决策规则

1. 安全缺陷、数据隔离缺陷和破坏标准 OIDC 互操作的问题优先于所有新增功能。
2. P0 只包含直接阻碍部署、接入、升级或排障的问题；P1 是已有接入方的明确需求；其余进入候选池。
3. 新能力开始前先提交设计：目标用户、边界、数据迁移、撤销语义、审计事件、兼容性和验收测试。
4. 每个小功能必须有风险匹配的自动验证，并在验证通过后独立提交。
5. Keycloak 互操作矩阵保持可选回归；标准测试向量、真实 HTTP 集成测试和 RP 样例是发布硬门槛。
6. 默认 HTTPS。仅完全受控的内网可以显式使用 HTTP，且不得跨公网、共享办公网或不受控 Wi-Fi，也不能将该结果作为公网部署验收。

## 6. 下一次开发迭代

下一次迭代只做“参考接入验收”中的一个可独立验证切片：先审阅 Keystone 的实际登录和资源服务授权路径，补齐其中最影响通用接入的缺口或自动化验收。当前已完成 Spring 资源服务参考样例：它先校验 Keylo JWT 的 issuer/audience，再调用 `/v1/authorize/check` 作最终 RBAC 决策。下一步应以该样例协助 Keystone 完成真实接入验收，或继续单实例运行基线。

这样能让 Keylo 以真实使用价值而非功能清单增长，同时保留未来向组织隔离、企业目录和多实例运行演进的清晰入口。
